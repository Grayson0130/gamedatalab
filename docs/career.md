# 职业与求职：把技能变成能审查的交付物

本页是岗位能力拆解和准备建议，不是 2026 实时职位清单，不暗示有公司正在招聘或保证录用。

| 方向 | 常见任务 | 作品证据 |
| --- | --- | --- |
| 游戏数据分析 | SQL 指标、活动复盘、漏斗、实验 | 成熟队列报告、可执行 SQL、决策摘要 |
| 产品/增长数据科学 | 因果推断、LTV、增量获客 | 随机留出设计、时间回测与收益区间 |
| 数据工程 | 遥测管道、调度、质量、成本 | 契约、幂等回放、坏消息处理 |
| 应用 ML | 流失、推荐、风控 | 时间切分、基线、误判与监控设计 |
| 游戏 AI 评估/本地化分析 | 多语言评测、标注、LQA、质量统计 | MQM 风格错误表、评审一致性、回归集 |

## 建议路线

第 1–2 周：先复现仓库案例，用自己的话说明 active user、D7、收入分母和退款口径；手写 SQL 交叉验证。

第 3–4 周：做一个新手漏斗与本地化体验案例。记录语言、UI 文本键、版本和错误严重度；将技术故障与语言问题分开。对于有游戏翻译与 LQA 背景的人，这比泛泛的预测模型更能展示领域判断。

第 5–6 周：扩展一个严格时间切分模型，比较基线与树模型。先写数据时点和收益函数，再选模型，不能用更多算法替代业务判断。

第 7–8 周：完成随机实验设计、灰度与风险说明，准备中英双语项目摘要。公开资料与合成数据可以展示方法，但不写成真实客户交付或线上收入提升。

## 面试自查

- 为什么新队列 D30 不应填 0？
- 为什么随机打散事件行会泄漏用户与未来信息？
- 为什么高 ROC AUC 不等于发优惠券有收益？
- 如何发现版本升级导致某语言事件丢失？
- 收入增长但退款、崩溃和长期留存恶化时如何决策？
- 同样数据下，你能用更简单、成本更低的方法回答问题吗？

## 展示方式

每个项目只突出一个决策：问题、数据来源与授权、口径、方法、结果、不确定性、建议和复现命令。附源代码、实际运行结果与失败边界。找工作时对照实际 JD 核验地区、合同、时区与技术要求，不将通用技能表当成招聘资格。
