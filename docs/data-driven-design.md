# 数据驱动的设计：玩法判断与实验闭环

原笔记将 OOP 与数据驱动对立，这不准确。面向对象描述软件组织方式；数据驱动架构将配置和内容与逻辑分离；产品分析则利用证据辅助设计。三者可以共存。

## 从问题到决策

以「新手在第二关退出较多」为例：

1. 检查版本、崩溃、加载失败和埋点丢失，确认退出并非技术故障。
2. 把漏斗拆成进入、首次失败、重试、完成；按设备和语言查看。
3. 结合录像、访谈与 LQA 判断提示是否难懂，不能仅凭相关性推断难度。
4. 将「改写提示能提高完成率」预注册为实验假设，固定一个主要指标。
5. 随机分流并记录暴露，审查 SRM、退出率、D7 留存和投诉。
6. 根据置信区间、最小业务收益和体验判断上线或回退；保留失败结果。

## 遥测架构建议

| 层 | 责任 | 不能默认相信的内容 |
| --- | --- | --- |
| 客户端 | 输入、界面、帧率、本地化上下文 | 本地时钟、付费成功、反作弊结论 |
| 权威服务端 | 对战状态、经济流水、订单验证 | 客户端上报余额 |
| 数据入口 | 契约、去重、限流、隔离坏消息 | 任意新增字段 |
| 数仓/指标层 | 版本化模型、回补、质量检查 | 口径随报表任意变更 |
| 决策层 | 实验、评审、灰度和回退 | 一次显著结果能永久成立 |

配置变更应记录生效时间、版本、目标受众和回退值；同一用户跨端需维持实验一致性。性能遥测高频采样，业务漏斗关键事件尽量完整收集，同时控制隐私与成本。

## Live Ops 与游戏经济

活动评估不能只看上线日 DAU。观察事件前后至少一个完整运营周期，区分促销拉动、奖励透支和下一周期回落。随机化活动资格或逐步上线时检查公会及社交溢出。

虚拟经济建立 source/sink 流水：货币产出、回收、存量、玩家财富分布、物价与交易集中度。奖励投放可能推高短期活跃却造成通胀。关卡平衡同时看尝试次数、失败原因、完成时间分布和无障碍体验。

Unity 2026 报告讨论了小规模项目、触达、跨端和 Live Ops。它是厂商样本中的观察，不能推断每种游戏都应改成长期运营，也不能把受访者意见当随机实验效果。[S3](sources.md)
