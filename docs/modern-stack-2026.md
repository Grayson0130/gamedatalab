# 2026 数据栈：按规模和问题选择

不以工具数量衡量成熟度。对学习作品集，能够解释指标、复现结果和控制泄漏，比堆叠流处理与大模型更重要。

## 三种规模

| 场景 | 建议起点 | 何时升级 |
| --- | --- | --- |
| 单人学习/小样本 | CSV/Parquet + SQLite/DuckDB + Python + 静态报告 | 内存、多人协作或定时运行成为瓶颈 |
| 小型在线产品 | 批量事件存储 + 托管 SQL/仓库 + 调度 + 指标层 | 延迟确有业务损失、数据量实测超限 |
| 多产品生产环境 | 对象存储/仓库、契约注册、编排、分层模型、权限与监控 | 跨团队责任、成本与合规需求明确 |

本仓库选择 SQLite 与 Python 标准库，避免先要求云账号。DuckDB 可用于本地列式分析；官方在 2026 年发布 1.5 系列，不应将此文中的任一版本永久写成「最新」。生产选型按发布说明与自身兼容测试锁定。[S7](sources.md)

## 批量与实时

默认先定义 SLA：运营日报允许小时级延迟，支付校验和实时作弊信号则可能需要秒级。Kafka/Flink 是选项，不是游戏数据的必选依赖。引入流处理意味着额外承担分区、重放、乱序、水位线与状态恢复。

所谓 exactly-once 要说明边界：传输重复与业务重复不是一回事。服务端订单幂等、事件 ID 去重、时间窗聚合和回补流程必须独立设计。

## 仓库、Lakehouse 和模型层

BigQuery、Snowflake、Redshift 是不同托管方案，应比较查询模式、存储地域、连接器、权限与真实成本。Iceberg/Delta Lake 是表格式与事务方案，不是独立完成治理的万能数据库。

分层建议：raw 保留来源与摄取时间；clean 校验与去重；mart 形成用户、订单和活动粒度事实；metric 固化分母与窗口。dbt 等变换工具可加入测试与血缘，但小型项目并不必须引入。

## 模型生命周期

记录数据快照、标签窗口、特征时点、训练配置、模型版本、离线评估、审批与回退版本。Feature Store 只有在在线/离线特征复用、延迟和一致性确有需求时才有价值。

监控覆盖新鲜度、缺失/重复、金额对账、模型校准、语言与渠道漂移、推理延迟、单位用户成本。LLM 应增加输出质量与检索来源检查，不得直接给予数据写入权限。

## 成本账本

至少记录每百万事件摄取成本、存储月成本、报表扫描字节、每日训练/推理费用与峰值预算。分区裁剪、增量聚合和日志保留策略通常应早于 GPU 采购。任何厂商价格都应在采购时重新核实，本文不提供未经核验报价。
