# 变现与 LTV：先统一收入与成本

广告、IAP、买断、订阅、DLC 和通行证的交易频率与生命周期不同，不适合用一个固定公式覆盖。「平均寿命×客单价」只能在严格假设下近似。

## 需要分开的量

| 名称 | 口径 | 用途 |
| --- | --- | --- |
| Gross bookings | 玩家付款额，注明含税与否 | 交易运营 |
| Net receipts | 扣退款后的收款，另注明平台费 | 渠道评估 |
| Recognized revenue | 按会计规则确认收入 | 财务报表，不能从遥测随意推导 |
| Contribution LTV | 收款扣平台、支付和服务等可变成本后的累计每新增玩家价值 | 获客与回本 |

金额用最小货币单位整数存储。多币种保留交易币、汇率日期与基准币金额；广告收入区分估算与结算。退款以订单及真实发生时间入账，避免重复扣除。

## 队列计算

```text
observed_LTV(H) = Σ(队列用户 D0..DH 净收入) / 原始新增用户数
contribution_LTV(H) = Σ(同窗口净额 - 可变成本) / 原始新增用户数
contribution_ROAS(H) = 同窗口贡献额 / 对应队列获客成本
```

本仓库 H=30 是 **D0–D30 共 31 个 UTC 日历日**，不是安装后精确 720 小时。未达到年龄 H 的用户不进入该 H 的估计分母。自然渠道零支出时 ROAS 未定义，展示 N/A；实际 CAC 还可能需要内容与人力成本。

## 从观测到预测

1. 先绘制渠道、版本、地区的成熟队列累计曲线。
2. 用历史队列 D7/D14 特征预测 D90，按队列时间回测。
3. 分开建模是否付费和付费金额，处理零膨胀与长尾；玩家层 bootstrap 计算不确定性。
4. 生存模型需处理右删失；BG/NBD 的购买与退出假设需检验，不默认适合赛季和强活动产品。
5. 对新赛季、价格、地区变化做压力测试。不能把存活用户收入当原始新增用户 LTV。

报告金额 MAE、分组偏差、区间覆盖率及关键分位数；只看 R² 不足以决定投放。买断游戏还需区分发售期、折扣期与 DLC 生命周期。

## 仓库案例与限制

[`sql/ltv.sql`](../sql/ltv.sql) 计算观测窗口净交易额，退款为负事件，假设统一 30% 平台费计算简化贡献 ROAS。**30% 是教学参数，不是所有商店的现行政策。** 未计税费、服务器、广告结算修订及客服成本，不等于完整利润。

通行证还应观察完成率、任务负担、退款与下一季回流，避免短期付费掩盖满意度下降。具体商店费用与规则按合同和官方页面复核。
